    readers, which use errors="replace". Writers are strict, readers are lenient.
  * rejects NUL bytes, C0 controls except \t\r\n, DEL (0x7F), and the UTF-16 BOM
    codepoints 0xFFFE/0xFFFF. Rejects bare CR and MIXED CRLF/LF.
  * records (encoding, newline, has_final_newline) and encode_source() round-
    trips all three.
  * _apply_operations deliberately clears has_final_newline when a batch deletes
    EVERY line, with a comment explaining why: an empty file cannot carry a
    line-ending style, so the encoded file would otherwise fail the publication
    validator. A genuinely subtle edge case, found and handled.
- STRONGEST PUBLICATION GUARANTEE in the folder: _write_source_atomically writes
  the temp, then RE-READS AND RE-DECODES it and compares `validated != document`
  structurally. So the published bytes are verified to decode back to exactly the
  intended document -- data equality, not just parseability. Strictly stronger
  than excel/powerpoint's re-load-and-parse. Also os.fsync() after the write
  (the only fsync in the folder), and `handle = -1` after os.fdopen so cleanup
  never double-closes.
- TRANSACTIONAL EDITING: _plan_operations validates EVERY operation against the
  ORIGINAL document first (exact match on expected_text, plus "line N is targeted
  more than once"), raises with "no changes were made because N operation(s) did
  not match", and only then does _apply_operations mutate. All-or-nothing, and
  the message is truthful because mutation is sequenced after validation.
- OPTIMISTIC CONCURRENCY (3rd family): exact expected_text per line, and the
  inspect tool emits json.dumps(line, ensure_ascii=False) so the model receives
  an exact escaped representation making byte-exact matching feasible.
  DIVERGENCE: source edits require EXACT equality; the pptx/xlsx editors use
  whitespace-normalized comparison. Different tolerance per family, undocumented.
- SourceEditOperation correctly enforces required fields per action and rejects
  any \r or \n in expected_text/new_text ("must contain exactly one line"), which
  is right for a line-oriented editor.
- _creation_stem honors whichever of config.suffixes the user asked for (so a
  .bash request keeps .bash rather than being forced to .sh) -- better than
  excel_create, which strips only .xlsx. Edit publishing preserves the SOURCE's
  actual suffix, and skips any candidate resolving to the source file.
- _prepare_session_directory matches excel_create's rule exactly: refuses when
  directory == root or not within root, so writes land in a session subdir only.
- VALIDATION OF LANGUAGES: _validate_document_lines runs config.line_validator
  over EVERY line, collects ALL problems, and reports a count plus up to 5
  examples rather than failing on the first. Called on create and on the edited
  document. This is the single hook that makes JSONL work.
- LAYOUT NIT (why the file is 1097 lines): `__all__` is defined at line 985 and

[batch 14: csv_edit.py]
- Uses stdlib csv.reader/csv.writer, NOT a naive split(","), so quoting, embedded

  to see embedded newlines correctly, and it is present in both places. Correct.
- _detect_delimiter: csv.Sniffer().sniff() over a 4096-byte sample restricted to
  ",;\t|", falling back to counting delimiter hits in the FIRST LINE, defaulting
  to ",". Preserves the uploaded file's separator; created files always use commas.
  Inspect output reports `Delimiter: {delimiter!r}` so the model learns it.
  RESIDUAL RISK: the fallback counts delimiters in the first line IGNORING QUOTES,
  so a quoted field containing commas can mislead it (csv.Sniffer runs first and
  usually wins, but the fallback itself has no quote awareness).

  temp with `_read_csv_document(temp_path, delimiter=document.delimiter)` -- the

  the round-tripped bytes and could pick a different separator for an ambiguous
  file, making validated != document fail spuriously. Deliberate and correct.
- CONFLICT LOGIC IS SUBTLE AND RIGHT: _plan_operations documents that a cell
  update conflicts with replace_row/delete_row on the same row, but NOT with

  updates on exactly those rows. Two passes keep it order-independent: bucket +
  duplicate detection first, then range/expected-value/conflict validation.
  "no changes were made because N operation(s) did not match" is truthful because
  mutation only happens after planning.
- _apply_operations applies cell updates FIRST, then structural row ops, so an
  insert_before_row on a cell-updated row emits the updated row second. Correct.
- CAPS ARE ENFORCED TWICE: _MAX_ROWS/_MAX_COLUMNS/_MAX_CELL_CHARS are checked at
